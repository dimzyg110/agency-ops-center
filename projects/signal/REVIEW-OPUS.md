# SIGNAL Phase 1 MVP — Strategic Product & SEO Review

**Reviewer:** Opus (Senior Product Engineer & SEO Expert)  
**Date:** 2026-02-12  
**Scope:** Strategic quality and production readiness for cannabis dispensary SEO  
**Files Reviewed:** All 18 source files in `src/`, `BUILD-SUMMARY.md`, `package.json`, `FINAL-PLAN.md`, `TECHNICAL-ARCHITECTURE.md`, `ch.yaml`

---

## Overall Verdict

**SIGNAL is an excellent architectural skeleton with the right bones, but it's currently a wireframe pretending to be a house.** The pipeline structure is correct (research → generate → review → humanize → publish), the GLASS integration concept is the right strategic bet, and the Git/PR publishing flow is perfectly suited for React/Netlify clients. However, the actual content generation, quality gating, humanization, and SEO mechanics are all stub-level implementations that would produce thin, generic content indistinguishable from any budget SEO agency's output. The gap between what the FINAL-PLAN promises and what the code delivers is significant — but bridgeable with focused iteration.

**Production readiness: 25/100** — The plumbing works. The water isn't flowing yet.

## Top 5 Strengths

### 1. Architecture Matches the Plan
The pipeline stages (research → generate → review → humanize → publish) map directly to the 6-stage content pipeline in FINAL-PLAN §3.1. The module boundaries are clean. Each stage is independently testable and replaceable. This is the right foundation.

### 2. Git/PR Publishing is Exactly Right
The `github-pr.ts` adapter is the correct approach for React/Netlify clients. Branch → commit → PR → merge → auto-deploy. No WordPress in sight. The implementation using Octokit is clean and follows the plan's architecture. This is one area where the MVP is genuinely production-capable.

### 3. GLASS Integration is Structurally Sound
The `GlassClient` class with typed interfaces (`GlassOperator`, `GlassPrice`, `GlassProduct`) provides a clean abstraction over the GLASS API. The data-injector pattern of transforming raw GLASS data into narrative context strings is the right architectural pattern, even though the current transformation is too shallow.

### 4. Multi-Client Config System is Correct
The Zod-validated YAML configuration with typed schema (`clientConfigSchema`) is the right approach. Separating tenant configs into `src/config/clients/*.yaml` means adding AC or Delivery is a new file, not new code. The schema enforces required fields while allowing client-specific customization.

### 5. No Scope Creep — Discipline on React/Netlify Only
The build summary explicitly states "No WordPress logic included" and the platform schema is locked to `z.literal("react-netlify")`. This is correct for Phase 1. The plan calls for WordPress adapters in Phase 2. The MVP respects that boundary.

## Top 5 Strategic Gaps

### 1. Content Templates Produce Skeleton Pages, Not Rankable Content

**This is the critical gap.** The FINAL-PLAN specifies location pages should be 1,500+ words with 7 required sections (hero, intro, getting_here, what_we_carry, pricing_snapshot, neighborhood_guide, FAQ, CTA). The actual `location-page.ts` template produces ~50 words of static text:

```tsx
<h1>Cannabis Healing in East Boston, MA</h1>
<p>Local average across tracked competitors is about $38.50.</p>
<p>Tracked inventory shows 145/200 products currently in stock across 6 categories.</p>
<p>Current market positioning suggests premium pricing pressure in this area.</p>
```

This is a data card, not a page. There are:
- No directions/getting_here section
- No neighborhood guide
- No FAQ section
- No product categories breakdown
- No CTAs
- No internal links
- No meta tags in the output
- No Spanish variant generation
- No H2 subheadings at all

The AI-generated narrative (`generateNarrative`) is only used for product pages, market reports, and blog posts — not location pages, which are the highest-priority content type. Location pages get only the three static GLASS summary strings.

**Impact:** These pages will not rank. Google rewards comprehensive, user-intent-matching content. A 50-word data snippet competes with nothing.

### 2. The Humanizer is a Find-and-Replace, Not a Pipeline

The FINAL-PLAN describes Stage 4 (Humanize) as "Style adaptation to client brand voice, removes robotic patterns, ensures local authenticity." The actual implementation:

```typescript
export function runHumanize(content: string): string {
  return content
    .replaceAll("Generated by SIGNAL", "Generated by SIGNAL (humanized pass)")
    .replaceAll("current market context", "fresh local market context")
    .replace(/\s{2,}/g, " ");
}
```

This is a placeholder, not a humanizer. It:
- Doesn't use LLM-based rewriting
- Doesn't apply brand voice from config
- Doesn't vary sentence structure
- Doesn't inject local colloquialisms or neighborhood knowledge
- Would fail any AI detection tool instantly
- Actually *adds* the string "Generated by SIGNAL" to the output (from the template comments)

**Impact:** Every piece of content will read identically robotic. AI-generated content that isn't humanized is increasingly penalized by Google's Helpful Content Update.

### 3. Quality Gate is a 3-Check Stub, Not a Quality System

The FINAL-PLAN specifies 11 automated quality checks (word count, keyword density, duplicate detection, readability, compliance, schema validation, internal links, meta tags, image alt text, data freshness, hallucination check). The actual `review.ts`:

```typescript
if (!content.includes("<h1")) issues.push("Missing H1.");
if (!content.includes("application/ld+json")) issues.push("Missing JSON-LD.");
if (content.length < 700) issues.push("Too short.");
```

Missing quality checks:
- No keyword density analysis
- No duplicate detection (cosine similarity)
- No readability scoring (Flesch-Kincaid)
- No cannabis compliance checking (medical claims, youth targeting)
- No schema validation (just checks for string presence)
- No internal link verification
- No meta tag length validation
- No data freshness check
- No hallucination detection

**Impact:** Content with incorrect schema, missing keywords, compliance violations, or duplicate text will pass review and get published.

### 4. Schema Markup is Syntactically Correct but Semantically Empty

The `schema-markup.ts` generates:

```json
{
  "@context": "https://schema.org",
  "@type": "LocalBusiness",
  "name": "Cannabis Healing",
  "areaServed": "East Boston",
  "url": "https://cannabishealing.com"
}
```

Compare to what the FINAL-PLAN specifies (§3.5):
- `@type: "Store"` (more specific than `LocalBusiness`)
- Full `PostalAddress` with street, city, state, zip
- `GeoCoordinates` with lat/lng
- `telephone`
- `openingHoursSpecification` with days and times
- `priceRange`
- `image`

The Product schema is equally thin — no `offers`, no `availability`, no `brand`, no `additionalProperty` for THC/CBD. The FAQPage schema type is defined but never generated in any template. BreadcrumbList is never generated.

**Impact:** Google Rich Results require specific required properties. A `LocalBusiness` without `address` won't generate a Knowledge Panel. A `Product` without `offers` won't show price in search results. FAQPage rich snippets — the plan's AEO cornerstone — are completely absent.

### 5. Research Module is GLASS-Only, Not SEO-Aware

The `research.ts` module:
1. Fetches operators from GLASS for a city
2. Fetches prices and products for the first operator
3. Returns raw data + a summary string

What it does NOT do (all specified in FINAL-PLAN §3.1, Stage 1):
- No SERP analysis (what currently ranks for the target keyword?)
- No "People Also Ask" scraping
- No competitor content gap analysis
- No existing content overlap check
- No Google Trends data
- No GSC data integration (what queries is the site already showing for?)
- No content brief generation (required sections, word count target, angle)
- No keyword intent classification (transactional vs. informational vs. local)

The research step only uses `config.keywords.primary[0]` — it doesn't match keywords to the specific content being generated. A location page for Chelsea and a product page for edibles would use the same keyword ("dispensary near logan airport").

**Impact:** Content is generated without understanding what the SERP landscape looks like. This means no competitive differentiation, no PAA-informed FAQs, and no keyword-to-content alignment.

## Content Quality Assessment

### Will this content rank? No, not in current form.

**Word count:** Templates produce 50-200 words. Google's top-ranking local dispensary pages average 1,500-3,000 words. The plan targets 1,500+. The code delivers ~5% of that.

**Content depth:** Location pages have zero navigational information, zero neighborhood context, zero FAQ content. Product pages have a single AI-generated paragraph. Blog posts have a single paragraph. Market reports have a summary + competitor count.

**E-E-A-T signals:** No author attribution, no "about us" context, no source citations, no review/testimonial integration, no expert quotes. Google's Quality Rater Guidelines emphasize Experience, Expertise, Authoritativeness, and Trustworthiness — none are present.

**GLASS data utilization:** Currently superficial. Three summary strings injected into location pages. No actual product tables, no price comparison data, no trend visualizations, no specific product names or prices. The FINAL-PLAN envisions pages with "215 products across 6 categories, with flower starting at $X — below the East Boston average of $Y." The code produces "Tracked inventory shows 145/200 products currently in stock across 6 categories."

**How GLASS data SHOULD appear:**
- Specific price tables by category (real numbers from GLASS)
- Named products with prices ("Blue Dream 3.5g — $35, 22% THC")
- Trend indicators ("Flower prices down 3% this month in East Boston")
- Competitive positioning ("Our average eighth: $38 vs. area average: $42")
- Product counts by category in a visual table
- "New this week" product highlights
- "Most popular" product rankings based on availability data

### AI Detection Risk: High

The templates embed "Generated by SIGNAL" as a comment in every file. The humanizer doesn't remove it (it transforms it to "Generated by SIGNAL (humanized pass)"). Beyond the literal watermark, the AI-generated paragraphs from `generateNarrative` use a single prompt with no style variation, no brand voice injection, and no structural diversity. Every blog post will have the same cadence.

## Keyword Strategy Assessment

### Current state: Static list, no intelligence

The keyword system is a flat YAML array:
```yaml
primary: ["dispensary near logan airport", "cannabis near boston airport", "east boston dispensary"]
location: ["weed near logan airport", "dispensary east boston ma"]
product: ["edibles near logan airport", "pre rolls east boston"]
```

**What's missing for real keyword intelligence:**
1. **Volume/difficulty data** — No search volume or keyword difficulty scores. The plan calls for this in the DB schema (`volume`, `difficulty` fields on `keywords` table).
2. **Dynamic keyword discovery** — No PAA scraping, no Google autocomplete mining, no "also searched for" analysis. The plan calls for this in the Research stage.
3. **Keyword-to-content mapping** — No system to ensure each page targets a unique primary keyword. Risk of keyword cannibalization across location pages.
4. **Long-tail generation** — No programmatic expansion of seed keywords (e.g., "dispensary near logan airport" → "dispensary open late near logan airport", "dispensary that delivers near logan airport").
5. **Seasonal/trending keywords** — No integration with Google Trends or GLASS trend data to surface timely keywords.
6. **Intent classification** — All keywords treated identically. "dispensary near logan airport" (transactional/local) requires fundamentally different content than "cannabis edibles dosage guide" (informational).

### Recommendation: Integrate Ahrefs API or SEMrush API for keyword data enrichment. The plan budgets $129/mo for Ahrefs Lite — use it.

## Internal Linking Assessment

### Current state: Random URL slicing, not topical authority

```typescript
export function suggestInternalLinks(keyword: string, existingUrls: string[]): InternalLink[] {
  return existingUrls.slice(0, 5).map((url) => ({
    text: `Related: ${keyword}`,
    href: url,
  }));
}
```

**Problems:**
1. Takes the first 5 URLs regardless of relevance. A product page about edibles would link to the first 5 URLs in the list, which might all be location pages.
2. All anchor text is identical: "Related: [keyword]". This is an SEO anti-pattern — Google may interpret uniform anchor text as manipulative.
3. No hub-and-spoke architecture. The plan specifies "every location page links to the regional hub AND 2-3 related location pages." The code has no concept of page hierarchy.
4. No link graph storage or recomputation. The plan specifies "link graph stored in SIGNAL's database and recomputed weekly."
5. No bidirectional linking. When a new page is published, existing pages should be updated to link to it. The code doesn't touch existing pages.
6. Links are never actually inserted into generated content — `suggestInternalLinks` is defined but never called by any template or generator.

**Impact:** Without proper internal linking, the site will have orphan pages that Google discovers slowly and ranks poorly. Topical authority (the plan's core SEO strategy) requires deliberate internal link architecture.

## Publishing Flow Assessment

### Is GitHub PR practical for a small team?

**Yes, with caveats.**

The current flow (one PR per content piece) is correct for Phase 1 where Randy reviews everything. However, at the plan's target of 78+ pages in 8 weeks, that's ~10 PRs per week. This is manageable but could create fatigue.

**Recommendations:**
1. **Batch PRs** — Group related content into single PRs (e.g., "5 East Boston location pages" as one PR with 5 files). The current code creates one PR per file.
2. **Auto-merge path** — For content that passes quality gates above a threshold score, offer auto-merge. The code doesn't implement this.
3. **PR templates** — Include quality score, GLASS data freshness, keyword targets, and preview links in PR descriptions. The current PR body is generic: "Automated publish from SIGNAL pipeline."
4. **Branch cleanup** — No mechanism to delete branches after merge. At 10+ PRs/week, stale branches will accumulate.

## Multi-Client Scaling Assessment

### Can this serve CH, AC, and future clients?

**Structurally yes, practically not yet.**

**What works:**
- YAML config per client with Zod validation
- Client slug used throughout for file organization and PR naming
- Template system is client-agnostic (passes `clientName`, `city`, etc.)

**What's missing for real multi-client:**
- **No AC or Delivery config files.** Only `ch.yaml` exists. This is fine for MVP.
- **Business type differentiation.** AC is a cultivator (B2B), not a dispensary. The templates are dispensary-centric (location pages, "dispensary near X"). AC needs strain guides, retailer locator pages, and wholesale content.
- **Platform config is locked to `react-netlify`.** Adding WordPress for Delivery requires schema changes.
- **Tone/voice is config-only, not enforced.** The LLM prompt includes `Tone: ${config.tone.voice}` but this is a weak signal. AC's "premium, heritage-forward, Aztec heritage" voice requires a very different prompt architecture than CH's "welcoming, local" voice.
- **GLASS data scoping.** Currently fetches operators by city. AC's use case is "which dispensaries carry AC products" — a completely different query pattern.

## Competitive Position vs. SERPCOM Prometheus

### Where SIGNAL currently wins:
1. **Data moat (conceptual)** — GLASS integration gives SIGNAL access to data no competitor has. Even in stub form, this is the right strategic bet.
2. **Platform flexibility** — Not locked to WordPress. Modern React/Netlify stack.
3. **Cost structure** — LLM-powered generation at ~$100-150/mo per tenant vs. manual agency work at $3-5K/mo.

### Where SIGNAL is currently WEAKER than Prometheus:
1. **Content volume and depth** — Prometheus pages are reportedly 200-400 words (thin). SIGNAL pages are currently ~50 words (thinner). Even bad Prometheus content beats this.
2. **Actually deployed** — Prometheus is live on client sites generating real rankings. SIGNAL has never published a page.
3. **Schema completeness** — Prometheus reportedly has Product schema (basic). SIGNAL's schema is even more basic.
4. **Town-name templating** — Prometheus at least swaps town names into substantive paragraphs. SIGNAL's location pages don't even have paragraphs.

### To actually beat Prometheus, SIGNAL needs:
1. Location pages that are 3-5x longer and deeper than Prometheus output
2. GLASS data visible in the content (specific prices, product counts, comparisons)
3. FAQ sections with FAQPage schema on every page
4. Real internal linking architecture
5. Content that's been humanized by LLM, not find-and-replace

## Recommended Improvements (Prioritized)

### P0 — Must Fix Before Any Content Goes Live

1. **Rebuild location page template to match FINAL-PLAN spec.** 7 sections, 1,500+ words, GLASS data tables, FAQ section, directions, neighborhood guide, CTAs, internal links. This is the single most impactful change.

2. **Replace humanizer with LLM-based rewriting.** Send generated content through a second LLM pass with brand voice instructions from config. At minimum: vary sentence structure, inject local references, remove robotic patterns, strip any "Generated by SIGNAL" markers.

3. **Complete schema markup with required properties.** LocalBusiness needs address, phone, hours, geo. Product needs offers with price/availability. FAQPage needs to actually be generated. Article needs author and dates. BreadcrumbList needs to be implemented.

4. **Wire AI generation into location pages.** Currently only product/blog/report pages use `generateNarrative()`. Location pages — the highest-priority content type — skip AI entirely and use only static GLASS summary strings.

5. **Implement FAQPage generation.** Create a PAA-informed FAQ generator that produces 5+ Q&As per page with proper FAQPage schema. This is the AEO strategy's foundation.

### P1 — Must Fix Before Week 2

6. **Expand quality gates** to include: keyword density check, word count per template type, schema validation (check required properties, not just string presence), cannabis compliance rules (regex for medical claims), duplicate detection (at minimum title/slug uniqueness).

7. **Build real internal linking engine.** Implement keyword-to-URL matching (not random URL slicing). Store link graph in DB. Insert links into generated content. Update existing pages when new content is published.

8. **Enrich research module** with PAA scraping (Firecrawl is budgeted at $19/mo), GSC data pull for existing keyword positions, and content brief generation.

9. **Add meta tag generation to all templates.** Title tags, meta descriptions, Open Graph, canonical URLs, hreflang for Spanish pages.

10. **Implement batch PR mode.** Group related content (e.g., all Week 2 location pages) into a single PR with summary of all pages included.

### P2 — Must Fix Before Month 2

11. **Integrate rank tracking.** Use Ahrefs API (budgeted) to pull keyword positions into `signal_rankings` table. Enable quick-win identification (positions 5-20).

12. **Add GSC Indexing API submission** post-publish. The code creates a PR but doesn't submit the resulting URL to Google.

13. **Build content refresh system.** When GLASS data changes significantly (price drops >10%, new products), flag affected pages for regeneration.

14. **Create AC and Delivery configs** with appropriate template variants (strain guides for AC, delivery zone pages for Delivery).

15. **Add observability.** Job logging, generation metrics, publish success/failure tracking. Currently errors are caught but only logged to console.

## One Bold Recommendation

### 🔥 Ship the GLASS Market Report First — Before Any Location Pages

The FINAL-PLAN's most underappreciated insight is in §5.4: *"Start with GLASS data content, not programmatic pages. Data content earns backlinks → backlinks build domain authority → authority makes location pages rank."*

The current code prioritizes location pages (the `generate` command defaults to "East Boston"). This is backwards.

**Instead:**

1. Make the `market-report` template the most polished, data-rich template in the system
2. Build it to produce a genuinely publishable 2,000-word report with real GLASS data tables, trend charts (as data, rendered client-side), methodology notes, and source attribution
3. Publish it on a GLASS public microsite (glass.report) — not on any client site
4. Pitch it to MJBizDaily, Leafly News, and Boston Globe cannabis reporters
5. The backlinks earned from this single piece power domain authority for ALL future client content

**Why this is bold:** It means delaying location page deployment by 1-2 weeks. But it means when those location pages DO go live, they're on a domain that already has authority. Without backlinks, even perfect location pages sit on page 3 indefinitely.

The market report is also the easiest template to make excellent — it's data-centric (GLASS's strength), it doesn't need humanization (it's analytical), and it positions Roviq as an industry data authority rather than another SEO agency pumping out location pages.

**Build the moat first. Then build the castle on it.**
